SERVICE数据库组 · Serverless

DynamoDB

数据库组Serverless按用量自带跨 AZ 高可用

Serverless 的键值和文档数据库：毫秒级读写，按需模式按请求收费，数据自动存在多个 AZ；全局表可以多区域同时读写。

常见用法

用户会话、购物车、游戏数据、高并发场景

为什么用它

访问方式固定、并发特别高时用它：没有数据库服务器要管，读写延迟稳定在毫秒级

核心知识点5 条

  1. Serverless 的键值和文档数据库，按主键（分区键加可选的排序键）访问，延迟稳定在个位数毫秒
  2. 容量模式：按需（按请求付费）和预置（可以配自动扩缩）
  3. 全局二级索引（GSI）、本地二级索引（LSI）支持别的查法；没有随意的多表关联查询，表结构要按访问方式设计
  4. DynamoDB Streams 按顺序记下每次改动，能触发 Lambda；全局表做多区域多活
  5. 时间点恢复（PITR）、TTL 到期自动删除；DAX 是专用的内存缓存

三个关键功能游戏里的三级升级，就是现实里的这三个功能

流量稳定时改成预置读写容量，配 Auto Scaling 自动调整，比按需便宜

游戏里：运行费或请求费减半

游戏里：免疫误删数据

游戏里：扛住整个 Region 出问题

和谁比、怎么选

Aurora 还是 DynamoDB

按键读写、并发特别高、访问方式固定，选 DynamoDB；要 SQL、事务、多表关联，选 Aurora（Serverless v2 会自动扩缩）

Aurora 还是 DynamoDB 还是 RDS

按键读写、超高并发选 DynamoDB；要 SQL 和事务选 Aurora（性能、高可用更好）或 RDS（引擎更多、更便宜）

DynamoDB 还是 ElastiCache

推荐结果要持久保存、按用户查，选 DynamoDB；要亚毫秒延迟、丢了能重算，选 ElastiCache

1.DynamoDB 单个项目最大是多少？
答案400 KB
大对象通常放 S3，表里存指针
2.Lambda、DynamoDB 这类 Serverless 服务，高可用要自己做多 AZ 吗？
答案不用，默认就在多个 AZ 里运行
Serverless 自带跨 AZ 高可用；要扛整个 Region 出问题，才需要自己做多区域
3.DynamoDB 的分区键选得不好会怎样？
答案请求集中到少数分区，形成热点被限流
分区键要选取值分散的字段
4.DynamoDB 全局表的特点是？
答案多个 Region 都能读写，自动同步
适合全球多活的业务
5.某游戏排行榜应用使用 Amazon DynamoDB，读请求非常多且可以接受最终一致性读取。现在需要把读取延迟从个位数毫秒降到微秒级，并尽量少改应用代码。应怎么做？SAA-C03
答案部署 DynamoDB Accelerator（DAX）集群
DAX 是与 DynamoDB API 兼容的托管内存缓存，可把最终一致读取的响应时间从毫秒级降到微秒级，代码改动很少。容量模式影响的是计费和扩展方式；全局二级索引用于支持其他查询模式；Streams 用于捕获数据变更，都不能把延迟降到微秒级。　官方文档 ↗
6.一个购物车应用需要无服务器、全托管的 NoSQL 数据库，用户量从 10 个涨到 1 亿个都要保持个位数毫秒的响应。应选择哪项服务？CLF-C02
答案Amazon DynamoDB
DynamoDB 是无服务器、全托管的分布式 NoSQL 数据库，在任何规模下都能提供个位数毫秒的性能。Redshift 是数据仓库，面向分析而非高并发的事务读写。　官方文档 ↗
7.一家初创公司推出新的移动应用，后端使用 Amazon DynamoDB。流量无法预测，可能长时间接近零，又会因营销活动突然暴涨。公司希望按实际请求付费且无需做容量规划。应如何配置表？SAA-C03
答案使用按需容量模式
按需模式按实际读写请求计费，自动适应流量变化，无需容量规划，适合不可预测的负载。按峰值预置在低谷期会浪费；预留容量适合稳定可预测的预置容量；DAX 用于降低延迟，并且会增加集群费用。　官方文档 ↗
