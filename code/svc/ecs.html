SERVICE容器组 · 容器

ECS

容器组容器按小时默认跨 AZ

亚马逊云科技自己的容器编排服务：告诉它要跑几个任务，它负责调度、替换坏掉的；底层可以用 EC2，也可以用 Fargate（不用管服务器）。

常见用法

微服务、批处理任务

为什么用它

想跑容器又不想学 Kubernetes 时选它，配 Fargate 连机器都不用管

核心知识点5 条

  1. 亚马逊云科技自研的容器编排：任务定义描述要跑哪些容器，服务（Service）保持任务数量、对接负载均衡
  2. 两种跑法：EC2（自己管机器）和 Fargate（Serverless，按任务的 vCPU 和内存计费）
  3. 服务默认把任务分散到多个 AZ
  4. 任务角色（task role）给容器授权访问别的服务
  5. 和 ECR、ALB、CloudWatch 直接打通，上手比 Kubernetes 简单

三个关键功能游戏里的三级升级，就是现实里的这三个功能

LV.1 · 第 1 级

Service Connect

同一命名空间里的 ECS 服务互相发现，代理自动做负载均衡、重试和异常检测；只管服务之间的调用，外部 API 不走这个代理

游戏里：过路费提高

LV.2 · 第 2 级

Fargate

不用管服务器：主机和操作系统由亚马逊云科技打补丁，也没有 SSH 可以登录；镜像里的漏洞还要靠 ECR 增强扫描

游戏里：这块不会被「暴露在公网的实例被 SSH 暴力破解」打中（别的实例照样会被打）

LV.3 · 第 3 级

服务自动扩缩

按 CPU 或请求数自动加减任务

游戏里：扛住流量暴增

和谁比、怎么选

EC2 还是 ECS

要完全掌控操作系统、跑老应用，用 EC2；已经容器化、想省心，用 ECS（配 Fargate 连机器都不用管）

ECS 还是 EKS

ECS 是亚马逊云科技自家的编排，简单好上手；团队熟 Kubernetes、要和别的环境保持一致，选 EKS

EC2 还是 ECS 还是 EKS

要完全掌控操作系统用 EC2；容器化了想省心用 ECS；团队熟 Kubernetes 选 EKS
