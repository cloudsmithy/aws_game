SERVICE应用集成组 · Serverless

SQS

应用集成组Serverless按用量自带跨 AZ 高可用

托管的消息队列：生产者把消息放进队列，消费者按自己的速度取。标准队列至少送达一次，FIFO 队列保证顺序。

常见用法

订单削峰填谷、把系统拆开互不拖累、异步任务

为什么用它

前后两段处理速度不一样时放一个队列：峰值先排队，后端按自己的节奏取，失败的还能重试

核心知识点5 条

  1. 托管消息队列：标准队列（吞吐几乎不限，至少投递一次，顺序尽量保持）和 FIFO 队列（严格按顺序，恰好处理一次）
  2. 可见性超时：消息被取走后一段时间别人看不到，处理完要删掉，不删就会重新出现
  3. 死信队列（DLQ）：多次处理失败的消息转进去，方便排查和重新投递
  4. 消息最长保留 14 天；长轮询能减少空轮询产生的请求费
  5. Lambda 能直接按批消费 SQS，失败的消息自动重试

三个关键功能游戏里的三级升级，就是现实里的这三个功能

1.SNS 和 SQS 的区别？
答案SNS 一对多推送，SQS 等消费者来拉
SNS 是发布订阅，SQS 是队列；常见组合是 SNS 扇出到多个 SQS 队列
2.SQS 有哪两种队列？
答案标准队列和 FIFO 队列
FIFO 按消息组保证顺序，5 分钟窗口内去重
3.SQS 消息最长能在队列里保留多久？
答案14 天
默认 4 天，最长 14 天
4.SQS 标准队列的投递保证是什么？
答案至少一次，可能重复、乱序
要严格顺序和去重用 FIFO 队列，消费端也要做幂等
5.订单系统的前端接收请求的速度经常远超后端处理速度，团队希望在两者之间放一个持久的消息队列来解耦组件。应选择哪项服务？CLF-C02
答案Amazon Simple Queue Service（Amazon SQS）
SQS 提供安全、持久、可用的托管队列，用于集成和解耦分布式系统组件。SNS 是推送式的发布订阅，没有让后端按自己的节奏去拉取的队列；Route 53 是 DNS 服务，KMS 管密钥，都与消息缓冲无关。　官方文档 ↗
6.某图片处理应用在促销期间请求激增。前端 Web 层直接同步调用后端处理服务，导致后端过载并丢失请求。如何改进架构以提升弹性？SAA-C03
答案前端把任务写进 SQS 队列，后端按积压量伸缩消费
SQS 队列缓冲突发请求，让前后端解耦，消息在处理前持久保存，后端 Auto Scaling 组可按队列积压量伸缩。加大实例规格仍有上限也无法缓冲；失败后立即反复重试会加剧过载；负载均衡器只转发请求，不会暂存请求。　官方文档 ↗
7.用户下单后，库存、计费和数据分析三个系统都需要各自独立、异步地处理同一个订单事件，任何一个系统暂时不可用都不能导致它丢失消息。哪种设计最合适？SAA-C03
答案SNS 主题扇出到三个系统各自的 SQS 队列
SNS 扇出会把同一消息复制推送到多个 SQS 队列，各系统独立消费，下游暂时不可用时消息留在自己的队列中。共用一个队列时，消息被一个消费者处理后就被删除；同步调用造成紧耦合；每小时扫描 S3 不够实时。　官方文档 ↗
