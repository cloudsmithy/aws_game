SQS

アプリケーション統合系サーバーレス従量課金マルチ AZ 標準対応

マネージドなメッセージキュー：プロデューサーがメッセージをキューに入れ、コンシューマーが自分のペースで取り出します。標準キューは少なくとも 1 回の配信、FIFO キューは順序を保証します。

主な用途

注文のピークの平準化、システムを疎結合にして互いに影響しないようにする、非同期タスク

使う理由

前後の処理速度が違うときに、間にキューを置きます：ピーク時はいったんキューにため、バックエンドは自分のペースで取り出します。失敗したものは再試行もできます

重要ポイント5 件

  1. マネージドなメッセージキュー：標準キュー（スループットはほぼ無制限、少なくとも 1 回の配信、順序はベストエフォート）と FIFO キュー（厳密な順序、1 回だけの処理）
  2. 可視性タイムアウト：受信されたメッセージは一定時間ほかのコンシューマーから見えなくなります。処理が終わったら削除する必要があり、削除しないと再び表示されます
  3. デッドレターキュー（DLQ）：何度も処理に失敗したメッセージを移しておき、調査や再送信をしやすくします
  4. メッセージは最長 14 日間保持されます。ロングポーリングを使うと、空振りのポーリングによるリクエスト料金を減らせます
  5. Lambda は SQS のメッセージをバッチで直接処理でき、失敗したメッセージは自動で再試行されます

1.SNS と SQS の違いはどれですか？

SNS はパブリッシュ/サブスクライブ、SQS はキューです。よくある組み合わせは、SNS から複数の SQS キューへのファンアウトです

FIFO はメッセージグループ内の順序を保証し、5 分間の期間内で重複を排除します
3.SQS のメッセージをキューに保持できる最長期間はどれですか？
正解14 日
デフォルトは 4 日、最長 14 日です
4.SQS 標準キューの配信保証はどれですか？

厳密な順序と重複排除が必要なら FIFO キューを使い、コンシューマー側も冪等にしましょう

正解Amazon Simple Queue Service（Amazon SQS）
SQS は安全で耐久性と可用性の高いマネージドキューを提供し、分散システムのコンポーネントの統合と疎結合化に使われます。SNS はプッシュ型のパブリッシュ/サブスクライブで、バックエンドが自分のペースでプルするためのキューはありません。Route 53 は DNS サービス、KMS はキーを管理するサービスで、いずれもメッセージのバッファリングとは関係ありません。　公式ドキュメント ↗

正解フロントエンドがタスクを SQS キューに書き込み、バックエンドはバックログの量に応じてスケールしながら処理する
SQS キューは突発的なリクエストをバッファリングしてフロントエンドとバックエンドを疎結合にし、メッセージは処理されるまで永続的に保存されます。バックエンドの Auto Scaling グループはキューのバックログに応じてスケールできます。インスタンスサイズを大きくしても上限があり、バッファリングもできません。失敗直後に再試行を繰り返すと過負荷が悪化します。ロードバランサーはリクエストを転送するだけで、一時的に保持することはありません。　公式ドキュメント ↗

SNS のファンアウトでは、同じメッセージが複製されて複数の SQS キューにプッシュされ、各システムが独立して処理します。ダウンストリームのシステムが一時的に利用できなくても、メッセージはそのシステム用のキューに残ります。1 つのキューを共有すると、メッセージは 1 つのコンシューマーが処理した時点で削除されます。同期呼び出しは密結合を生みます。1 時間ごとの S3 スキャンではリアルタイム性が不十分です。　公式ドキュメント ↗
