ELB

ネットワーク系マネージド時間課金マルチ AZ 標準対応

ロードバランシング：トラフィックを背後の複数の EC2、コンテナ、Lambda に分散し、異常なターゲットを自動的に避けます。ALB は HTTP/HTTPS、NLB は TCP/UDP を処理します。

主な用途

ウェブサイトや API の統一された入口、マルチ AZ の高可用性

使う理由

複数のバックエンドの前に統一された入口を置きます：トラフィックを自動で振り分け、故障したインスタンスを避けます。最初から複数の AZ にまたがっています

重要ポイント5 件

  1. 主に 3 種類：ALB（レイヤー 7、パスやホスト名に基づいて HTTP と HTTPS を転送）、NLB（レイヤー 4 の TCP と UDP、低レイテンシーで固定 IP も使える）、GWLB（サードパーティのセキュリティアプライアンスを経路に組み込む）
  2. ヘルスチェックで、異常なターゲットからトラフィックを自動的に外します。ロードバランサー自体も複数の AZ にまたがっています
  3. ALB では、WAF の関連付け、Cognito によるサインインとの連携、TLS のオフロード（証明書は ACM で無料発行）ができます
  4. Auto Scaling グループとの連携：新しく起動したインスタンスが自動でターゲットグループに登録されます
  5. 時間とキャパシティユニット（LCU）に応じて課金されます

3 つの主な機能ゲームの 3 段階のアップグレードは、実際のサービスにあるこの 3 つの機能です

LV.1 · レベル 1

HTTPS + ACM

ACM の無料証明書で HTTPS を有効にし、証明書は自動で更新されます

ゲーム内：証明書の期限切れを無効化

運用コスト：1 周ごとに $10

LV.2 · レベル 2

LCU 予約

ロードバランサーキャパシティユニット（LCU）を事前に予約し、予測できるトラフィックのピークに耐えられるようにします

ゲーム内：パフォーマンス効率の柱 +1 点

運用コスト：1 周ごとに $20

LV.3 · レベル 3

負荷分散 + Auto Scaling

ターゲットグループを EC2 Auto Scaling グループにアタッチします。ヘルスチェックで異常なインスタンスが見つかると Auto Scaling が自動で新しいものに置き換え、トラフィックが増えるとターゲットあたりのリクエスト数に応じて自動でインスタンスを追加します

ゲーム内：あなたの EC2 は「EC2 インスタンスのハードウェア廃止」と「単一障害点」を無効化（異常なインスタンスは自動で置き換え）

運用コスト：1 周ごとに $30

比較と選び方

CloudFront か ELB

ユーザーが世界中にいて静的コンテンツが多いなら、Shield を CloudFront に適用します。1 つのリージョンだけで、動的なリクエストが中心なら ALB に適用します

3.一般公開されているウェブサイトが Application Load Balancer の背後にデプロイされています。最近、一部の IP アドレスが短時間に大量の HTTP リクエストを送信して API に過剰なアクセスを繰り返していることがわかりました。最小限の運用作業でこれらの IP を自動的に制限するにはどうすればよいですか？SAA-C03
正解ALB に WAF ウェブ ACL を関連付け、レートベースのルールを追加する
WAF のレートベースのルールは IP などの単位でリクエストを集計し、しきい値を超えると自動的にレート制限をかけるため、リストを手作業で管理する必要はありません。セキュリティグループは許可ルールしかサポートしていません。NLB はレイヤー 4 で動作するため、HTTP レイヤーの悪用を識別できません。フローログを手作業で分析してからネットワーク ACL を変更する方法は対応が遅く、運用上のオーバーヘッドも大きくなります。　公式ドキュメント ↗
4.あるウェブアプリケーションは、単一のアベイラビリティーゾーンにある 3 台の EC2 インスタンスで実行されており、その前段に ALB があります。以前、アプリケーションのプロセスがハングしたにもかかわらず EC2 のステータスチェックは正常のままで、一部のリクエストが失敗したことがありました。アベイラビリティーゾーンレベルの回復力を高めると同時に、異常なインスタンスを自動的に置き換えるにはどうすればよいですか？SAA-C03
正解Auto Scaling グループを複数のアベイラビリティーゾーンにまたがって構成し、ELB ヘルスチェックを有効にする
複数のアベイラビリティーゾーンにまたがる Auto Scaling グループは、いずれかのアベイラビリティーゾーンに障害が発生してもキャパシティを維持できます。ELB ヘルスチェックを有効にすると、アプリケーション層で異常なインスタンスも自動的に置き換えられます。インスタンスを大きくしても、単一のアベイラビリティーゾーンに依存するリスクはなくなりません。EC2 のステータスチェックではアプリケーション層の障害を検出できず、アラームだけでは結局手作業での対応が必要です。シンプルルーティングはヘルスチェックを行いません。　公式ドキュメント ↗
5.ある会社はモノリシックなアプリケーションを複数のマイクロサービスに分割し、1 つのドメイン名で、URL パス（/api/orders、/api/users など）に応じて HTTP リクエストを別々のターゲットグループに転送したいと考えています。どのロードバランサーを使用すべきですか？SAA-C03
正解Application Load Balancer で、パス条件に基づくリスナールールを設定する
ALB はレイヤー 7 で動作し、リスナールールで path-pattern 条件をサポートしているため、URL パスに応じて別々のターゲットグループにルーティングできます。NLB はレイヤー 4 で動作するため、URL パスを認識できません。Gateway Load Balancer はサードパーティの仮想ネットワークアプライアンスをデプロイするためのものです。複数の CLB とドメイン名を使う方法では、1 つのドメイン名という要件を満たしません。　公式ドキュメント ↗
6.あるリアルタイムのマルチプレイヤーゲームは独自の UDP プロトコルを使用しており、毎秒数百万件のリクエストを極めて低いレイテンシーで処理する必要があります。また、顧客がファイアウォールの許可リストに追加できるよう、アベイラビリティーゾーンごとに固定 IP アドレスを提供する必要があります。どのロードバランサーを選ぶべきですか？SAA-C03
正解Network Load Balancer で、サブネットごとに Elastic IP を 1 つ関連付ける
NLB はレイヤー 4 で動作して UDP をサポートし、毎秒数百万件のリクエストを処理でき、アベイラビリティーゾーンごとに静的 IP を提供します。インターネット向けの場合は Elastic IP を関連付けることもできます。ALB は HTTP/HTTPS 向けで、UDP はサポートしていません。CLB がサポートするのは HTTP、HTTPS、TCP、SSL のみです。インスタンスの IP を手作業で登録する方法では、スケーリングに合わせて自動的に更新できません。　公式ドキュメント ↗
7.運用チームは、EC2、ロードバランサー、データベースなどのリソースを 1 つのテンプレートに記述し、ワンクリックで同じ環境を繰り返し作成したいと考えています（Infrastructure as Code）。どのサービスを使用すべきですか？CLF-C02
正解CloudFormation
CloudFormation では、必要なリソースをテンプレートに記述すると、そのプロビジョニングと設定を CloudFormation が行います。作成されたリソースの集まりはスタックと呼ばれます。Cost Explorer はコストの分析に使うもので、リソースは作成できません。　公式ドキュメント ↗
