Aurora

データベース系PaaS時間課金マルチ AZ は自前で構成

Amazon Web Services が独自に開発したクラウドネイティブなリレーショナルデータベースで、MySQL および PostgreSQL と互換性があります：データは 3 つの AZ に 6 つのコピーとして保存され、リードレプリカは最大 15 個。Aurora Serverless v2 は負荷に応じて自動でスケールし、Global Database はリージョンをまたいで使えます。

主な用途

高い同時実行性が求められる基幹業務データベース

使う理由

より高いパフォーマンスと可用性を備えた MySQL や PostgreSQL が必要なときに選びます：ストレージは自動で 3 つの AZ にまたがり、リードレプリカの遅延も小さく抑えられます

重要ポイント5 件

  1. MySQL・PostgreSQL 互換のクラウドネイティブなデータベース：ストレージ層は 3 つの AZ に 6 つのコピーを保存し、使用量に応じて自動で拡張します
  2. 低レイテンシーのリードレプリカを最大 15 個作成でき、プライマリインスタンスに問題が起きると、レプリカが自動でプライマリに昇格します
  3. Aurora Serverless v2 は負荷に応じてキャパシティ（ACU）を自動でスケールします
  4. Global Database はリージョン間でレプリケーションし、遅延は通常 1 秒未満です。リージョン単位の災害対策に使えます
  5. Zero-ETL 統合で、データをほぼリアルタイムに Redshift へ同期して分析できます

3 つの主な機能ゲームの 3 段階のアップグレードは、実際のサービスにあるこの 3 つの機能です

LV.1 · レベル 1

マルチ AZ

ほかの AZ に Aurora レプリカを追加し、プライマリインスタンスに障害が起きると自動でフェイルオーバーします。ストレージはもともと 3 つの AZ に 6 つのコピーを保存しており、シングル AZ なのはコンピューティングインスタンスだけです

比較と選び方

Aurora か DynamoDB

キーで読み書きし、同時アクセスが非常に多く、アクセスパターンが決まっているなら DynamoDB を選びます。SQL、トランザクション、複数テーブルの結合が必要なら Aurora を選びます（Serverless v2 は自動でスケールします）

Aurora か RDS

Aurora は MySQL と PostgreSQL に互換性があり、パフォーマンスと可用性がより高くなります（ストレージは 3 つの AZ にまたがります）。SQL Server や Oracle が必要な場合や、コストを抑えたい場合は RDS を使います

Aurora か DynamoDB か RDS

キーでの読み書きで同時アクセスが非常に多いなら DynamoDB を選びます。SQL とトランザクションが必要なら Aurora（パフォーマンスと可用性がより高い）か RDS（エンジンが多く、より安い）を選びます

Aurora か OpenSearch

ベクトルが多く、キーワードとベクトルを組み合わせたハイブリッド検索が必要なら OpenSearch を選びます。すでに PostgreSQL を使っていて、データ量が多くないなら Aurora（pgvector）を選びます

4.Aurora Global Database のリージョン間レプリケーションの遅延は、通常どの程度ですか？
正解1 秒未満

5.グローバルに事業を展開する SaaS 企業が Amazon Aurora MySQL を使用しています。2 つ目のリージョンで低レイテンシーの読み取りを提供し、プライマリリージョンに障害が発生した場合は、ごくわずかなデータ損失（1 秒程度）でそのリージョンで書き込みを再開できる必要があります。最も適切な方法はどれですか？SAA-C03
正解Aurora Global Database で、2 つ目のリージョンにセカンダリクラスターを追加する
Aurora Global Database は専用のインフラストラクチャを使ってリージョン間でレプリケートし、レイテンシーは通常 1 秒未満です。セカンダリリージョンではローカルでの読み取りが可能で、リージョン間のスイッチオーバーやフェイルオーバーもサポートしています。同じリージョン内のレプリカではリージョンの障害に対応できません。1 時間ごとのスナップショットや毎日の DMS による移行では、RPO が要件を大幅に超えます。　公式ドキュメント ↗
6.あるアプリケーションは Amazon Aurora PostgreSQL を使用しており、レポートのクエリがライターインスタンスのリソースを大量に消費しています。会社は読み取り専用のクエリをオフロードし、今後レプリカを追加・削除してもアプリケーションの接続設定を変更しなくて済むようにしたいと考えています。どうすればよいですか？SAA-C03
正解Aurora レプリカを追加し、レポートのクエリをクラスターのリーダーエンドポイントに接続する
リーダーエンドポイントは、すべての Aurora レプリカの間で読み取り専用の接続を負荷分散するため、レプリカを追加・削除してもアプリケーションの設定を変更する必要はありません。クラスターエンドポイントはライターインスタンスを指します。スナップショットから頻繁に復元したクラスターはデータがリアルタイムでなく、運用も複雑です。ライターインスタンスをスケールアップするだけでは、レポートの負荷を分離できません。　公式ドキュメント ↗
