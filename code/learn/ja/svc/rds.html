SERVICEデータベース系 · PaaS

RDS

データベース系PaaS時間課金マルチ AZ は自前で構成

マネージドなリレーショナルデータベース：MySQL、PostgreSQL、MariaDB、Oracle、SQL Server、Db2 に対応し、バックアップ、パッチ適用、フェイルオーバーを代行します。マルチ AZ 配置では別の AZ にスタンバイインスタンスを置きます。

主な用途

従来型の業務システム、EC サイトの注文データベース

使う理由

リレーショナルデータベースが必要だけれど、自分で運用したくないときに使います：バックアップ、パッチ適用、マルチ AZ のフェイルオーバーはすべてマネージドで、選べるエンジンが最も多いです

重要ポイント5 件

  1. マネージドなリレーショナルデータベースで、エンジンは MySQL、PostgreSQL、MariaDB、Oracle、SQL Server、Db2 から選べます
  2. マルチ AZ 配置：別の AZ のスタンバイインスタンスに同期レプリケーションし、プライマリに問題が起きると自動でフェイルオーバーします（スタンバイインスタンスは通常、読み取りリクエストを受け付けません）
  3. リードレプリカ：非同期レプリケーションで読み取りトラフィックを分担します。別のリージョンに置くこともできます
  4. 自動バックアップとポイントインタイムリカバリに対応し、バックアップは最長 35 日間保持できます。手動スナップショットは長期間残せます
  5. RDS Proxy はデータベース接続を再利用するので、Lambda のように接続が多く、1 回あたりの時間が短い呼び出し元に向いています

比較と選び方

Aurora か RDS

Aurora は MySQL と PostgreSQL に互換性があり、パフォーマンスと可用性がより高くなります（ストレージは 3 つの AZ にまたがります）。SQL Server や Oracle が必要な場合や、コストを抑えたい場合は RDS を使います

Aurora か DynamoDB か RDS

キーでの読み書きで同時アクセスが非常に多いなら DynamoDB を選びます。SQL とトランザクションが必要なら Aurora（パフォーマンスと可用性がより高い）か RDS（エンジンが多く、より安い）を選びます

4.ある企業の本番データベースは Amazon RDS for MySQL 上で常時稼働しており、今後 3 年間はインスタンスタイプもリージョンも変わりません。データベースのコストを削減するにはどうすればよいですか？SAA-C03
正解このデータベース用に 3 年契約の RDS リザーブド DB インスタンスを購入する
RDS リザーブド DB インスタンスは、1 年または 3 年の期間をコミットすることで、オンデマンド料金に比べて大幅な割引を受けられるため、長期間安定して稼働するインスタンスに適しています。本番データベースをスポットで実行すると中断のリスクがあり、運用の負担も大きくなります。常時稼働の本番データベースは夜間に停止できません。RDS のストレージでは S3 のストレージクラスを使用できません。　公式ドキュメント ↗

正解スタンバイインスタンスが別のアベイラビリティーゾーンにあり、障害時に自動でフェイルオーバーする
スタンバイインスタンスが 1 つのマルチ AZ デプロイはフェイルオーバーをサポートしますが、スタンバイインスタンスは読み取りトラフィックを処理しません。読み取りパフォーマンスをスケールするには、リードレプリカなどの別の方法を検討します。　公式ドキュメント ↗
6.あるアプリケーションは Amazon RDS for MySQL を使用しており、データベースのパスワードは現在設定ファイルにハードコードされています。会社は、認証情報を一元的に保存して定期的に自動ローテーションすること、そして独自に開発するコードをできるだけ減らすことを求めています。どの方法を採用すべきですか？SAA-C03
正解認証情報を Secrets Manager に保存して自動ローテーションを有効にし、アプリケーションは実行時に API で読み取る
Secrets Manager は認証情報を一元的に保存でき、自動ローテーション（マネージドローテーションまたは Lambda ローテーション関数）が組み込まれているため、アプリケーションは必要なときに最新の値を読み取れます。Parameter Store を使う方法では、ローテーション用のスクリプトを自分で書く必要があります。KMS のキーローテーションは暗号化キーのキーマテリアルを置き換えるだけで、データベースのパスワードは変更しません。　公式ドキュメント ↗
7.ある e コマース企業の注文データベースは、単一の Amazon RDS for PostgreSQL インスタンスで稼働しています。この会社は、アベイラビリティーゾーンに障害が発生したときに自動的にフェイルオーバーし、コミット済みのデータをできるだけ失わないことを求めていますが、読み取りのスケーリング機能を追加する必要はありません。どのように変更すべきですか？SAA-C03
正解この DB インスタンスをマルチ AZ デプロイに変換する
マルチ AZ デプロイでは、別のアベイラビリティーゾーンに同期レプリケーションされたスタンバイインスタンスが維持され、プライマリインスタンスに障害が発生すると自動的にフェイルオーバーします。リードレプリカは非同期レプリケーションのため、手動での昇格が必要で、最新のデータが失われる可能性があります。1 時間ごとのスナップショットでは RPO が最大 1 時間になり、復旧にも手作業が必要です。　公式ドキュメント ↗
8.あるニュースサイトの Amazon RDS データベースでは、同じ人気クエリが何度も繰り返し実行されるため、CPU 使用率が高止まりしています。これらのクエリの結果は数分間ほとんど変わりません。データベースへの変更をできるだけ抑えつつ読み取りパフォーマンスを向上させるにはどうすればよいですか？SAA-C03
正解ElastiCache で人気クエリの結果をキャッシュする
ElastiCache はマネージドのインメモリキャッシュを提供し、繰り返し実行される人気クエリの結果をキャッシュすることで、データベースの負荷と読み取りのレイテンシーを大幅に削減できます。マルチ AZ DB インスタンスのスタンバイインスタンスは読み取りを処理しません。マルチ AZ DB クラスターのリーダーインスタンスは読み取りを分担できますが、新しいクラスターへの移行が必要なうえ、人気クエリは毎回あらためて実行されます。st1 は HDD で、データベースのランダム I/O には適していません。T 系に変更しても CPU の課金とバーストの仕組みが変わるだけで、繰り返し実行される人気クエリの負荷は残ります。　公式ドキュメント ↗
