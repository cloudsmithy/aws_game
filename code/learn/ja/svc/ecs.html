ECS

コンテナグループコンテナ時間課金デフォルトでマルチ AZ

Amazon Web Services 独自のコンテナオーケストレーションサービス：実行するタスク数を指定すると、スケジューリングと故障したタスクの置き換えを行います。基盤には EC2 も Fargate（サーバー管理が不要）も使えます。

主な用途

マイクロサービス、バッチ処理

使う理由

コンテナを動かしたいけれど Kubernetes は学びたくない、というときに選びます。Fargate と組み合わせれば、マシンの管理さえ不要です

重要ポイント5 件

  1. Amazon Web Services 独自のコンテナオーケストレーション：タスク定義で実行するコンテナを記述し、サービス（Service）がタスク数を維持してロードバランサーと連携します
  2. 実行方法は 2 種類：EC2（マシンを自分で管理）と Fargate（サーバーレス、タスクの vCPU とメモリに応じて課金）
  3. サービスはデフォルトでタスクを複数の AZ に分散します
  4. タスクロール（task role）で、コンテナにほかのサービスへのアクセス権限を付与します
  5. ECR、ALB、CloudWatch と直接連携でき、Kubernetes より簡単に使い始められます

3 つの主な機能ゲームの 3 段階のアップグレードは、実際のサービスにあるこの 3 つの機能です

LV.1 · レベル 1

Service Connect

同じ名前空間の ECS サービスが互いを検出し、プロキシが負荷分散、再試行、外れ値検出を自動で行います。対象はサービス間の呼び出しだけで、外部 API はこのプロキシを通りません

ゲーム内：通行料アップ

運用コスト：1 周ごとに $10

LV.2 · レベル 2

Fargate

サーバーの管理は不要です。ホストと OS には Amazon Web Services がパッチを適用し、SSH でログインすることもできません。イメージ内の脆弱性には引き続き ECR の拡張スキャンが必要です

ゲーム内：このマスは「公開インスタンスが SSH ブルートフォース攻撃で破られた」の対象にならない（ほかのインスタンスは対象になる）

運用コスト：1 周ごとに $20

LV.3 · レベル 3

サービスの自動スケーリング

CPU やリクエスト数に応じてタスクを自動で増減します

ゲーム内：トラフィックの急増に耐える

運用コスト：1 周ごとに $30

比較と選び方

EC2 と ECS

OS を完全に制御したい、古いアプリケーションを動かしたいなら EC2 を使います。すでにコンテナ化していて手間を減らしたいなら ECS を使います（Fargate と組み合わせればマシンの管理さえ不要です）

ECS と EKS

ECS は Amazon Web Services 独自のコンテナオーケストレーションで、シンプルで始めやすいのが特長です。チームが Kubernetes に慣れていて、ほかの環境と構成をそろえたいなら EKS を選びます

EC2 と ECS と EKS

OS を完全に制御したいなら EC2、コンテナ化していて手間を減らしたいなら ECS、チームが Kubernetes に慣れているなら EKS を選びます
