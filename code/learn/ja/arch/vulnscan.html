データの流れ3 ステップ

  1. 01

    ECR にイメージがプッシュされると Inspector がすぐに脆弱性をスキャン（⇄）

  2. 02
    → 次へ進む

    ECS、EKS または EC2 には重大な脆弱性のないイメージだけをデプロイ。稼働後も Inspector が監視を続け、新たに公表された CVE も検出

  3. 03
    + 連携するオプション

    Inspector の検出結果を EventBridge に送り、担当者への自動通知やチケットの起票を行う

各サービスの役割6 つのサービス

01ECR必須

コンテナ · マネージド · 従量課金 · 価格 $180
ここでの役割
ECR にイメージがプッシュされると Inspector がすぐに脆弱性をスキャン
使う理由
イメージをデプロイ先のすぐそばに置けます：ECS や EKS と権限が連携していて、プッシュ時には脆弱性もあわせてスキャンします
概要
マネージドなコンテナイメージレジストリ：Docker / OCI イメージを保存し、脆弱性をスキャンできます。ECS と EKS はここから直接イメージをプルします。
主な用途
CI/CD でビルドしたイメージをプッシュし、デプロイ時にプル

02Inspector必須

セキュリティ · マネージド · 従量課金 · 価格 $380
ここでの役割
Inspector の検出結果を EventBridge に送り、担当者への自動通知やチケットの起票を行う
使う理由
EC2、コンテナイメージ、Lambda の脆弱性を自動で検出します。新しい CVE が公開されても、誰かがスキャンするのを待つ必要はありません
概要
自動脆弱性スキャン：EC2、ECR のコンテナイメージ、Lambda 関数を継続的にスキャンし、ソフトウェアの脆弱性や意図せず公開されたネットワークポートを見つけ、リスクに応じてスコアを付けます。
主な用途
パッチ管理、コンプライアンスチェック

03ECS必須いずれか 1 つ

コンテナ · コンテナ · 時間課金 · 価格 $180
ここでの役割
ECS、EKS または EC2 には重大な脆弱性のないイメージだけをデプロイ
使う理由
コンテナを動かしたいけれど Kubernetes は学びたくない、というときに選びます。Fargate と組み合わせれば、マシンの管理さえ不要です
概要
Amazon Web Services 独自のコンテナオーケストレーションサービス：実行するタスク数を指定すると、スケジューリングと故障したタスクの置き換えを行います。基盤には EC2 も Fargate（サーバー管理が不要）も使えます。
主な用途
マイクロサービス、バッチ処理
ECS のサービスノート →

03EKS必須いずれか 1 つ

コンテナ · コンテナ · 時間課金 · 価格 $200
ここでの役割
ECS、EKS または EC2 には重大な脆弱性のないイメージだけをデプロイ
使う理由
チームがすでに Kubernetes を使っていて、Helm やコミュニティのツールを引き続き使いたいときに選びます
概要
マネージド Kubernetes：コントロールプレーンは Amazon Web Services が複数の AZ で実行し、クラスターごとに時間単位で課金されます。ワーカーノードには EC2、マネージド型ノードグループ、Fargate、Auto Mode を使えます。
主な用途
すでに Kubernetes を使っているチームのクラウド移行、複数環境への統一的なデプロイ
EKS のサービスノート →

03EC2必須いずれか 1 つ

コンピューティング · IaaS · 時間課金 · 価格 $100
ここでの役割
ECS、EKS または EC2 には重大な脆弱性のないイメージだけをデプロイ
使う理由
OS を完全に制御したい、特殊なソフトウェアを入れたい、古いアプリケーションを動かしたいときに使います。インスタンスタイプの種類が最も豊富です
概要
クラウド上の仮想サーバー：CPU、メモリ、OS を自分で選び、秒単位で課金されます。オンデマンド、Savings Plans、スポットなどの方法で購入できます。各インスタンスは 1 つの AZ にあるため、高可用性には複数の AZ にそれぞれ数台ずつ配置し、ELB と Auto Scaling を組み合わせます。
主な用途
さまざまなアプリケーションの実行、OS を完全に制御する必要があるケース
EC2 のサービスノート →
どれを選ぶか

OS を完全に制御したいなら EC2、コンテナ化していて手間を減らしたいなら ECS、チームが Kubernetes に慣れているなら EKS を選びます

04EventBridgeオプション

アプリケーション統合 · サーバーレス · 従量課金 · 価格 $240
ここでの役割
Inspector の検出結果を EventBridge に送り、担当者への自動通知やチケットの起票を行う
使う理由
イベントを送る側と処理する側が互いを知る必要がありません：処理する側を追加しても送信側を変更する必要がなく、スケジュールに従って起動することもできます
概要
サーバーレスのイベントバス：Amazon Web Services のサービス、自社のアプリケーション、SaaS から送られるイベントをルールに従って Lambda や Step Functions などに転送し、スケジュールでの起動もできます。
主な用途
イベント駆動型アーキテクチャ、アカウント間のイベント配信、定期実行タスク

ゲーム内での計算方法

必須
3 つ：ECR、Inspector、ECS または EKS または EC2
オプション
1 つ：EventBridge。なくても完成扱いで、あればまとめて請求
請求方法
そろえると、ほかのプレイヤーがこのアーキテクチャに含まれるあなたのマスのどれに止まっても、アーキテクチャ全体のすべてのサービスの通行料を合計して請求します。「または」のサービスを複数持っていれば、すべて合計に含まれます
金額の目安
アップグレードなし、出目 7 での見積もり：最小構成なら毎回約 $132、すべての部分をそろえると（最適なアーキテクチャ）約 $256。アップグレードすると、さらに大きく増えます
追加ボーナス
「重大な CVE が公表」を無効化
