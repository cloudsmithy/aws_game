SQS

Application Integration groupServerlessBy usageMulti-AZ built in

Managed message queue: producers put messages in the queue and consumers take them at their own pace. Standard queues deliver at least once; FIFO queues guarantee order.

Common uses

Smoothing order spikes, decoupling systems so they don't drag each other down, asynchronous tasks

Why use it

Put a queue between two stages that process at different speeds: peaks wait in the queue, the backend pulls at its own pace, and failed messages can be retried

Key concepts5 points

  1. Managed message queues: standard queues (nearly unlimited throughput, at-least-once delivery, best-effort ordering) and FIFO queues (strict ordering, exactly-once processing)
  2. Visibility timeout: after a message is picked up, others can't see it for a while; delete it after processing, or it will reappear
  3. Dead-letter queue (DLQ): messages that fail processing repeatedly are moved there for troubleshooting and redrive
  4. Messages are kept for up to 14 days; long polling cuts the request fees caused by empty polls
  5. Lambda can consume SQS messages directly in batches, and failed messages are retried automatically

1.What is the difference between SNS and SQS?
AnswerSNS pushes one-to-many, while SQS waits for consumers to pull
SNS is publish/subscribe and SQS is a queue; a common combination is SNS fanning out to multiple SQS queues
2.What are the two kinds of SQS queues?
AnswerStandard queues and FIFO queues
FIFO guarantees order within a message group and deduplicates within a 5-minute window
3.How long can an SQS message stay in the queue at most?
Answer14 days
4 days by default, 14 days at most
4.What is the delivery guarantee of an SQS standard queue?
AnswerAt least once, possibly duplicated and out of order
For strict ordering and deduplication use a FIFO queue, and make the consumer idempotent too
5.The front end of an order system often receives requests much faster than the back end can process them, and the team wants to place a durable message queue between them to decouple the components. Which service should they choose?CLF-C02
AnswerAmazon Simple Queue Service (Amazon SQS)
SQS provides a secure, durable, and available managed queue for integrating and decoupling distributed system components. SNS is push-based publish/subscribe and has no queue from which the back end can pull at its own pace; Route 53 is a DNS service and KMS manages keys, so neither is related to message buffering. 6.An image processing application sees a surge in requests during a promotion. The front-end web tier calls the back-end processing service directly and synchronously, which overloads the back end and loses requests. How can the architecture be improved for elasticity?SAA-C03
AnswerThe front end writes tasks to an SQS queue, and the back end scales its consumption based on the backlog
An SQS queue buffers bursts of requests, decouples the front end from the back end, and stores messages durably until they are processed, and the back-end Auto Scaling group can scale on the queue backlog. A larger instance size still has a limit and can't buffer; retrying immediately and repeatedly after failures makes the overload worse; a load balancer only forwards requests and does not hold them. Official docs ↗
7.After a user places an order, the inventory, billing, and analytics systems each need to process the same order event independently and asynchronously, and the temporary unavailability of any one system must not cause it to lose messages. Which design is the most suitable?SAA-C03
AnswerAn SNS topic fans out to a separate SQS queue for each of the three systems
SNS fanout copies and pushes the same message to multiple SQS queues, each system consumes independently, and when a downstream system is temporarily unavailable, messages stay in its own queue. With a shared queue, a message is deleted once one consumer processes it; synchronous calls create tight coupling; scanning S3 every hour is not real-time enough. Official docs ↗
