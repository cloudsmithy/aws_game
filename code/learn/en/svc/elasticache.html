ElastiCache

Database groupPaaSBy the hourMulti-AZ is on you

Managed in-memory cache: Valkey, Redis OSS and Memcached, with reads and writes in microseconds to milliseconds, placed in front of the database to absorb hot reads.

Common uses

Caching hot data, sessions, leaderboards

Why use it

When the same data is read over and over, add an in-memory cache layer: sub-millisecond responses and much less load on the database

Key concepts5 points

  1. Managed in-memory database, with Valkey, Redis OSS, and Memcached engines
  2. Common uses: caching hot data (check the cache first, and query the database on a miss), session storage, leaderboards, and counters
  3. Valkey and Redis OSS support replicas, Multi-AZ automatic failover, and data persistence; Memcached is a simple cache only, with no persistence
  4. With ElastiCache Serverless you don't choose node sizes, and it's billed by usage
  5. Give cached data an expiration time, and invalidate the matching cache entries after the database changes

Compare and choose

DynamoDB or ElastiCache

If recommendations must be stored durably and looked up by user, choose DynamoDB; if you need sub-millisecond latency and lost results can be recomputed, choose ElastiCache

3.A news website's Amazon RDS database has constantly high CPU because the same popular queries run over and over, and the query results barely change for several minutes. How can read performance be improved with as few changes to the database as possible?SAA-C03
AnswerCache the results of popular queries with ElastiCache
ElastiCache provides a managed in-memory cache, and caching the results of repeated popular queries significantly reduces database load and read latency. The standby instance of a Multi-AZ DB instance deployment does not serve reads; the reader instances of a Multi-AZ DB cluster can share reads, but you must migrate to a new cluster, and popular queries still run in full every time; st1 is HDD and is not suited to random database I/O; switching to a T-series instance only changes how CPU is billed and bursts, and the load from repeated popular queries remains.
