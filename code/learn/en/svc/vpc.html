VPC

Networking groupManagedFreeMulti-AZ built inWildcard service

Your private network in the cloud: you define the CIDR range, subnets, route tables and security groups, and decide which resources can reach the internet. The VPC itself is free.

Common uses

Put the public-facing load balancer in a public subnet, and the application and database in private subnets

Why use it

Put resources in your own private network, where subnets and security groups decide who can reach them, so databases don't have to be exposed to the internet

Key concepts5 points

  1. Your own private network: pick a CIDR block and split it into subnets by AZ; a public subnet's route table points to an internet gateway
  2. A private subnet reaches the internet through a NAT gateway (placed in a public subnet, billed by the hour and by data processed)
  3. Security groups: instance-level, stateful, allow rules only; network ACLs: subnet-level, stateless, both allow and deny rules
  4. VPC endpoints keep traffic off the public internet: gateway endpoints (S3 and DynamoDB, free) and interface endpoints (PrivateLink, available for most services)
  5. Connect VPCs with VPC peering or Transit Gateway; VPC Flow Logs record traffic going in and out

3.A Lambda function connected to a VPC in a private subnet needs to call Secrets Manager. The VPC has no internet gateway or NAT gateway, and the security policy also forbids traffic from passing through the internet. What should you do?SAA-C03
AnswerCreate an interface VPC endpoint for Secrets Manager
Secrets Manager supports private access from within a VPC through interface endpoints (PrivateLink), with no need for an internet gateway or NAT. Gateway endpoints support only S3 and DynamoDB; a NAT gateway sends traffic out to the internet; VPC peering doesn't support transitive routing, so you can't borrow the other VPC's egress. 4.A company has 40 VPCs and a VPN connection to its on-premises data center. It needs central interconnection so that all VPCs can reach the on-premises network, but the development VPCs and production VPCs must be network-isolated from each other. Which approach has the least operational overhead?SAA-C03
AnswerUse Transit Gateway, and associate the development and production VPCs with different route tables
Transit Gateway acts as a central hub connecting VPCs and the VPN, and can divide the network into isolated routing domains using multiple route tables. Full-mesh peering involves a huge number of connections and is hard to manage; VPC peering doesn't support transitive routing, so on-premises can't be reached through a transit VPC; going over the internet doesn't meet the private interconnection requirement. Official docs ↗
5.A company accesses a VPC through one Direct Connect connection. The business requires connectivity to continue if Direct Connect goes down, but the budget is limited and the company can accept lower reliability and performance on the backup link. What is the most cost-effective approach?SAA-C03
AnswerConfigure a Site-to-Site VPN as a backup connection
Site-to-Site VPN builds an IPsec tunnel over the internet and can serve as a low-cost backup for Direct Connect, at the price of lower reliability and performance. Multiple dedicated connections at multiple locations give the highest resilience, but also the highest cost; VPC peering only connects VPCs and can't reach an on-premises data center; a NAT gateway only does address translation and is not a link by itself, so traffic to on-premises still has to go over VPN or Direct Connect. Official docs ↗
6.Which statement about security groups and network ACLs in a VPC is correct?CLF-C02
AnswerSecurity groups are stateful and return traffic is automatically allowed; network ACLs are stateless
Security groups are stateful, so return traffic is automatically allowed; network ACLs are stateless, so return traffic must be explicitly allowed. The official recommendation is to use security groups as the primary control and network ACLs as a supplementary subnet-level control. Official docs ↗
7.EC2 instances in a private subnet transfer tens of TB of data per month to Amazon S3 in the same Region through a NAT gateway, and the NAT gateway's data processing charges are high. How can costs be reduced most effectively while keeping the instances private?SAA-C03
AnswerCreate a gateway VPC endpoint for S3 and add it to the private subnet's route table
An S3 gateway endpoint directs traffic to S3 through the route table, bypassing the NAT gateway, and gateway endpoints carry no additional charge. NAT instances must be operated yourself and are a single point of failure; moving to a public subnet violates the private requirement; Transfer Acceleration speeds up long-distance transfers and does not reduce NAT charges. Wildcard service
VPC can be attached as long as the architecture has one service that can connect to a VPC: any service from the compute, containers, database, storage, analytics, or AI groups, or ELB or API Gateway (Lambda can connect to a VPC, API Gateway can do private APIs, and S3 and DynamoDB go through VPC endpoints); optional services and one-of-several services all count. VPC cannot be attached to an architecture made up only of security, monitoring, Route 53, CloudFront, and application integration (SQS, EventBridge, Step Functions) services
