Step Functions

Application Integration groupServerlessBy usageMulti-AZ built in

Visual workflow orchestration: chains Lambda, container tasks and API calls to many services into a state machine, with built-in retries, branching and parallelism, and can pause to wait for human approval.

Common uses

Order processing flows, data processing pipelines, orchestrating the steps of AI agents

Why use it

No need to write your own state machine for multi-step processes: retries, timeouts and rollback on failure can be configured for each step, and you can see which step a run has reached

Key concepts5 points

  1. Visual workflow orchestration: a state machine describes the steps, branches, parallel paths, and waits
  2. Two workflow types: Standard (runs for up to one year, exactly-once execution, suited to long processes) and Express (up to 5 minutes, high throughput, billed by number of executions and duration)
  3. Every step can have retries, timeouts, and error catching that routes to compensation logic
  4. Can call many services' APIs directly (SDK integrations), so not everything has to go through Lambda
  5. Execution history is visual and shows each step's input and output, which makes troubleshooting easy

Three key featuresThe game's three upgrade levels are these three real-world features

LV.1 · Level 1

Express workflows

Suited to high-frequency, short workflows that finish within 5 minutes: billed by number of executions and run duration (scaled by memory), not by state transitions, so it's cheaper when there are many steps that run fast

3.Several microservices at a company publish order status change events. The requirement is to route events to different targets (such as Lambda and Step Functions) based on event content (for example, a status field equal to CANCELLED), without changing publisher code when adding consumers, and with as little routing code as possible. Which service should it use?SAA-C03
AnswerAn Amazon EventBridge event bus, with a rule that has an event pattern for each type of consumer
EventBridge rules use event patterns to match events by content and route them to targets, and adding a consumer only requires adding a rule. Hard-coded routing in the publisher creates coupling; Kinesis requires each consumer to read and filter on its own; a self-built broker has high operational overhead. Official docs ↗
