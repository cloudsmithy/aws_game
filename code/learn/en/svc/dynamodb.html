DynamoDB

Database groupServerlessBy usageMulti-AZ built in

Serverless key-value and document database: millisecond reads and writes, on-demand mode billed per request, data automatically stored across multiple AZs; global tables allow reads and writes in multiple Regions at once.

Common uses

User sessions, shopping carts, game data, high-concurrency workloads

Why use it

Use it when access patterns are fixed and concurrency is very high: there are no database servers to manage, and read and write latency stays steady at the millisecond level

Key concepts5 points

  1. Serverless key-value and document database, accessed by primary key (a partition key plus an optional sort key), with consistent single-digit millisecond latency
  2. Capacity modes: on-demand (pay per request) and provisioned (can be paired with auto scaling)
  3. Global secondary indexes (GSI) and local secondary indexes (LSI) support other query patterns; there are no ad hoc multi-table joins, so design tables around your access patterns
  4. DynamoDB Streams records every change in order and can trigger Lambda; global tables are multi-Region and multi-active
  5. Point-in-time recovery (PITR) and automatic TTL deletion of expired items; DAX is a purpose-built in-memory cache

Compare and choose

Aurora or DynamoDB

For key-based reads and writes, very high concurrency and fixed access patterns, choose DynamoDB; for SQL, transactions and joins across tables, choose Aurora (Serverless v2 scales automatically)

Aurora or DynamoDB or RDS

For key-based reads and writes at very high concurrency, choose DynamoDB; for SQL and transactions, choose Aurora (better performance and high availability) or RDS (more engines, lower cost)

DynamoDB or ElastiCache

If recommendations must be stored durably and looked up by user, choose DynamoDB; if you need sub-millisecond latency and lost results can be recomputed, choose ElastiCache

AnswerRequests concentrate on a few partitions, creating hot spots that get throttled
Choose a partition key with widely distributed values

5.A game leaderboard application uses Amazon DynamoDB, has a very high volume of reads, and can accept eventually consistent reads. It now needs to cut read latency from single-digit milliseconds to microseconds, with as few application code changes as possible. What should it do?SAA-C03
AnswerDeploy a DynamoDB Accelerator (DAX) cluster
DAX is a managed in-memory cache compatible with the DynamoDB API, and it can cut the response time of eventually consistent reads from milliseconds to microseconds with very few code changes. The capacity mode affects billing and how scaling works; a global secondary index supports other query patterns; Streams captures data changes; none of these can bring latency down to microseconds. 6.A shopping cart application needs a serverless, fully managed NoSQL database that keeps single-digit millisecond response times as users grow from 10 to 100 million. Which service should it choose?CLF-C02
AnswerAmazon DynamoDB
DynamoDB is a serverless, fully managed, distributed NoSQL database that delivers single-digit millisecond performance at any scale. Redshift is a data warehouse built for analytics, not for high-concurrency transactional reads and writes. Official docs ↗
7.A startup is launching a new mobile app with an Amazon DynamoDB backend. Traffic is unpredictable: it may stay near zero for long periods and then surge suddenly because of a marketing campaign. The company wants to pay for actual requests and avoid capacity planning. How should the table be configured?SAA-C03
AnswerUse on-demand capacity mode
On-demand mode bills for actual read and write requests, adapts to traffic changes automatically, and needs no capacity planning, which suits unpredictable workloads. Provisioning for peak wastes money during troughs; reserved capacity suits steady, predictable provisioned capacity; DAX is for reducing latency and adds cluster costs. Official docs ↗
