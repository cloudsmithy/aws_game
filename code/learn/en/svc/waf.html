WAF

Security groupManagedBy usageMulti-AZ built in

Web application firewall: sits in front of CloudFront, ALB, or API Gateway and blocks SQL injection, cross-site scripting, and malicious bots by rule. It can also rate-limit by IP.

Common uses

Defending against common web attacks, preventing API abuse

Why use it

Blocks SQL injection, XSS, malicious bots and API abuse with rules at the entry point, without changing application code

Key concepts5 points

  1. Web application firewall: sits in front of CloudFront, ALB, API Gateway, AppSync, Cognito user pools, and more
  2. Rules are set in a Web ACL: IP sets, geographic location, rate limiting (rate-based), and managed rule groups (common vulnerabilities, known bad inputs, SQL injection, and more)
  3. Bot Control identifies and manages crawlers; Fraud Control protects against credential stuffing and fraudulent sign-ups
  4. Billed by Web ACL, number of rules, and number of requests
  5. Run a new rule in Count mode first to observe it, and switch it to Block once you've confirmed it causes no false positives

1.Which services can WAF be placed in front of?
AnswerCloudFront, ALB, API Gateway
WAF works at layer 7; on API Gateway it can only be attached to REST APIs, and it can also be attached to AppSync, Cognito user pools, and more
2.What is a WAF managed rule group?
AnswerReady-made rules maintained by Amazon Web Services or partners
For example, protection against common vulnerabilities and lists of known malicious IPs
3.A public-facing website is deployed behind an Application Load Balancer. Recently, a few IP addresses were found sending large numbers of HTTP requests in a short time to hammer the API. How can these IPs be restricted automatically with the least operational effort?SAA-C03
AnswerAssociate a WAF web ACL with the ALB and add a rate-based rule
A WAF rate-based rule counts requests by dimensions such as IP and automatically throttles them when the threshold is exceeded, with no need to maintain a list by hand. Security groups only support allow rules; an NLB works at layer 4 and can't detect abuse at the HTTP layer; manually analyzing flow logs and then editing the network ACL is slow and costs a lot of operational effort.
