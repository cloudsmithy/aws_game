Aurora

Database groupPaaSBy the hourMulti-AZ is on you

Amazon Web Services' own cloud-native relational database, compatible with MySQL and PostgreSQL: data is stored as 6 copies across 3 AZs, with up to 15 read replicas; Aurora Serverless v2 scales automatically with load, and Global Database can span Regions.

Common uses

High-concurrency core business databases

Why use it

Choose it when you need MySQL or PostgreSQL with higher performance and availability: storage spans 3 AZs automatically, and read replicas have low lag

Key concepts5 points

  1. Cloud-native database compatible with MySQL and PostgreSQL: the storage layer keeps 6 copies across 3 AZs and grows automatically with usage
  2. Up to 15 low-latency read replicas; if the primary instance has a problem, a replica is promoted to primary automatically
  3. Aurora Serverless v2 scales capacity (ACU) up and down automatically with load
  4. Global Database replicates across Regions, usually with under 1 second of latency, and can be used for Region-level disaster recovery
  5. Zero-ETL integrations sync data into Redshift in near real time for analytics

Compare and choose

Aurora or DynamoDB

For key-based reads and writes, very high concurrency and fixed access patterns, choose DynamoDB; for SQL, transactions and joins across tables, choose Aurora (Serverless v2 scales automatically)

Aurora or RDS

Aurora is compatible with MySQL and PostgreSQL and has better performance and high availability (storage spans 3 AZs); for SQL Server or Oracle, or to save money, use RDS

Aurora or DynamoDB or RDS

For key-based reads and writes at very high concurrency, choose DynamoDB; for SQL and transactions, choose Aurora (better performance and high availability) or RDS (more engines, lower cost)

Aurora or OpenSearch

For many vectors and hybrid search that combines keywords and vectors, choose OpenSearch; if you already use PostgreSQL and the data volume is small, choose Aurora (pgvector)

AnswerUnder 1 second

5.A global SaaS company uses Amazon Aurora MySQL. It needs low-latency reads in a second Region, and if the primary Region fails, it needs to resume writes in that Region while losing very little data (about 1 second). Which approach is the most suitable?SAA-C03
AnswerAn Aurora global database, with a secondary cluster in the second Region
Aurora global database replicates across Regions using dedicated infrastructure, typically with latency under 1 second, the secondary Region can serve local reads, and it supports cross-Region switchover or failover. Replicas in the same Region can't protect against a Region failure; the RPO of hourly snapshots and daily DMS migrations is far larger than required. Official docs ↗
6.An application uses Amazon Aurora PostgreSQL, and reporting queries consume a lot of the writer instance's resources. The company wants to offload read-only queries, and wants to avoid changing the application's connection settings when replicas are added or removed later. What should it do?SAA-C03
AnswerAdd Aurora Replicas and have the reporting queries connect to the cluster's reader endpoint
The reader endpoint load-balances read-only connections across all Aurora Replicas, so adding or removing replicas requires no application configuration changes. The cluster endpoint points to the writer instance; clusters frequently restored from snapshots hold data that is not real-time and are complex to operate; scaling up only the writer instance does not isolate the reporting load.
